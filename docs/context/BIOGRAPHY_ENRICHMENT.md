# Наполнение биографий (ALE-510)

Путь: «Обслуживание данных» → «Наполнение данных» → «Биографии».
Роуты: `/data-maintenance`, `/data-maintenance/enrichment`, `/data-maintenance/enrichment/biographies`.
Модуль независим от импорта новых кавалеров, оптимизации изображений и updater.
Landing «Обслуживание данных» показывает работающий раздел наполнения и отдельный неактивный placeholder «Оптимизация изображений — В разработке», без dead link.

## Контракт

- Статистика читает текущую SQLite в одной read-транзакции. Пустота — NULL, пустая строка или Unicode whitespace. В каждой группе исходной иерархии наград считаются уникальные person.id; группы нельзя суммировать.
- Выгрузка выбирает только существующих кавалеров с пустой biography, в порядке person.id. До 5 000 строк, XLSX до 10 МБ, распакованное содержимое до 50 МБ. Формулы не генерируются даже из строк базы, начинающихся с `=`.
- Исходные ФИО, год, звание, награда, иерархия и номера сопровождаются подписанным snapshot кавалера и его наград. Подпись привязана к пути SQLite. Перемещение базы или очистка временного ключа требует новой выгрузки. Схема SQLite не меняется.
- Новый XLSX v2: основной видимый лист содержит ровно семь колонок — ID кавалера, ФИО, Год рождения, Награда, Биография, Источник, Статус. Исходные звание, полная иерархия, номера/все награды и HMAC snapshot находятся на скрытом листе «Служебные данные». Скрытие — удобство представления, не граница доверия: при импорте подпись и соответствие текущей SQLite проверяются заново. Подпись v2 включает версию контракта; v1 нельзя выдать за упрощённый формат.
- Внешнее заполнение меняет только Биографию, Источник и Статус. «Найдено» — явное утверждение автора файла: источник подтверждает именно этого кавалера по ФИО, достоверному году и награде. «Требует проверки», пустой/неизвестный статус при непустом тексте не дают права записи. Excel содержит подсказку/validation статусов; сервер проверяет их независимо. Приложение не вызывает ИИ/API и не проверяет внешнюю страницу автоматически. Owner отдельно подтверждает принадлежность источников при сохранении.
- Пользовательские шаги: «Скачать Excel» → «Загрузить заполненный Excel» → «Проверить и сохранить». Preview группирует строки в «Готово к сохранению», «Требует проверки», «Пропущено», показывая конкретную причину. Пустой текст, заполненная biography и несуществующий ID пропускаются. Дубли ID, неизвестные статусы, расхождения исходных ФИО/года/награды/подписи требуют проверки. Неизвестный год и возможный default 1945 всегда блокируют автоматическую запись. Лимит 2 500 Unicode символов включает пробелы и переносы; текст не обрезается. Понятная ошибка повреждённой структуры Excel показывается прямо в шаге 3, без записи.
- Сохранение требует отдельного checkbox-подтверждения, разрешённого write_mode и выключенного read_only. В `BEGIN IMMEDIATE` повторно проверяются исходные данные, существование person_id и текущая пустота biography. Обновляется только biography, только у строк, ранее показанных как допустимые. Строка, ставшая допустимой после preview, автоматически в подтверждённую группу не добавляется.
- Допустимая часть смешанного файла применяется явно; конфликтная часть остаётся без изменений. Ошибка записи отменяет всю транзакцию допустимой части. Повторный commit и повторная загрузка не перезаписывают заполненные тексты.
- Preview и отчёты с источниками/evidence доступны 7 дней. Пользователь скачивает Excel-отчёт с категориями, причинами и сведениями о проверке; старый JSON endpoint сохранён для совместимости. Временные записи хранятся в пользовательской временной папке ОС вне SQLite/media/install. Для постоянного хранения отчёт нужно скачать. При прерывании между подготовкой отчёта и commit итог помечается неопределённым; требуется новый preview. Ошибка финального сохранения отчёта после commit сообщается как сохранённые данные с предупреждением, без ложного заявления о rollback.

## Совместимость ALE-491

Прежний исследовательский XLSX без встроенных подписанных данных принимается только вместе с подписанной исходной выгрузкой нового модуля, содержащей те же ID. Самодостаточные подписанные выгрузки первого формата продолжают проверяться по прежнему строгому контракту. Заголовки могут находиться в строке 5 после исторической сводки. Формулы внутри строк данных запрещены; исторические формулы сводки не исполняются.

Для v2 mapping: «ID кавалера» → person_id, «Биография» → biography, «Источник» → source_url, «Статус» → status; identity/hierarchy/signature читаются из скрытого листа.

Для прежнего формата mapping: «Биография» → biography, «WarHeroes URL» → source_url, «Статус» → status, «Подтверждённые факты» → notes. «ФИО в карточке», «Год в карточке», «Идентификация» сохраняют значение. Для принятого формата пилота evidence «ФИО, реальный год и награда совпали» заменяет отсутствующую отдельную колонку награды источника. Явно описанные в «Сверка звания» различия раннего и позднего звания показываются, но не меняют звание SQLite. Для прежнего формата существенное несовпадение звания блокируется. В новом формате исходное звание остаётся в подписанных метаданных и сверяется с текущей SQLite; отдельного редактируемого поля звания источника в семи видимых колонках нет.

Автоматические тесты используют только TEMP SQLite/media. Фактический принятый XLSX ALE-491 проверяется на TEMP-копии его исходных identity-полей: 20 строк, 19 допустимых, 1 конфликт. В Git нет реальных персональных данных, XLSX и browser artifacts.
