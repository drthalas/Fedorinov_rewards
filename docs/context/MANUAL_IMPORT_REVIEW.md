# ALE-513 — двухвкладочный импорт BIO/годов (26.10.2026)

## Экран наполнения: экспорт, импорт и статистика (27.10.2026)

Общий заголовок «Наполнение данных», затем постоянные счётчики всей базы: всего,
с BIO, без BIO. Расчёт непосредственно по person, без join наград; null/пустой
текст/пробелы — отсутствие BIO. После commit и при возврате сводка обновляется
отдельным read-only запросом, не сбрасывая файл, вкладку, позицию или итог.

Два открытых блока: «Экспорт данных» с выбором группы/объёма и «Импорт данных»
с одним picker заполненного XLSX. Экспорт работает в фоне: фактические обработанные
записи → формирование XLSX → готовый файл/100%. Формирование без измеримого процента
показывается отдельно; готовность файла не означает сохранение на компьютер.
Статус переживает reload, повторный POST той же операции не запускает вторую
выгрузку; скачивание читает проверенные готовые bytes. SQLite открывается read-only,
схема семи колонок, hidden sheet и HMAC не меняются. Экспорт не очищает импорт.

Удалённый UI input `original` передавал вторую исходную подписанную выгрузку для
старого развёрнутого формата, где заполненный файл не содержал snapshot/signature.
Backend строит по ней originals[person_id], проверяет HMAC и сверяет исходную
личность/награды с SQLite. Этот compatibility API сохранён; обычный UI его больше
не предлагает. Актуальный XLSX сам содержит signed hidden sheet и работает через
один picker. Старый файл без проверяемого snapshot отклоняется с предложением
скачать актуальный шаблон; подпись не обходится и не создаётся заново для импорта.

`/data-maintenance/enrichment/biographies`: выбор XLSX автоматически проверяет файл.
Две вкладки «Готово к импорту» и «Недостаточно данных», по 50 строк. Ручных решений
по строкам/ФИО/годам нет. Все подтверждённые дополнения staging до единственной нижней
«Импортировать» → сводка точных изменений/пропусков → общее явное подтверждение.
Нерешённые записи не блокируют безопасные. Фактические no-op показаны отдельно как
«Без изменений», не считаются нехваткой доказательств. После своего commit повтор
не создаёт запись; собственная последовательная HMAC receipt chain продолжает тот
же immutable export без ложного stale.

Пустая BIO ≤2500 символов и любой отличающийся достоверный год источника готовы
автоматически. 1945 не имеет особого права на изменение; настоящий 1945 сохраняется.

## Owner correction 27.10.2026 — операция и завершение

Confirmation → importing → saving → success/failure. После финального подтверждения
UI синхронно показывает устойчивый progress-screen без «К списку». Backend выполняет
тот же atomic commit в background job; done/total — фактически обработанные кавалеры,
процент ≤99 до commit. Фаза «Сохраняем изменения…» предшествует commit, успех/100%
подтверждаются только существующим атомарным batch receipt. Retry/refresh запрашивают
статус того же operation, запись не отправляется вслепую. Прерванный/неизвестный
исход не выдаётся за успех; актуальные HMAC/stale/rollback guards сохранены.

Отдельный итог скрывает preview/picker/старые счётчики и обещания. Числа уникальных
кавалеров, BIO, годов и пропусков вычисляются из реально записанных events. «К списку»
после успеха только обновляет readonly результаты, сохраняет tab/page/scroll и не
запускает повторную запись. Повторный вход восстанавливает завершённый результат из
журнала, включая ранее завершённые операции; no-op сообщается прямо.

## ALE-521 — диагностика запрета без изменения данных

`workspace.fatal` — общий запрет: хотя бы одна строка не прошла исходный guard.
Число подготовленных изменений не доказывает пригодность всего XLSX. При fatal
UI сообщает «Проверка остановлена», перечисляет ID/причины и даёт JSON всех строк;
не обещает запись подготовленных строк. Категории отделяют отсутствующий snapshot,
отсутствующую/неверную подпись, повреждённый формат, protected changes, stale identity,
конкурентные изменения, audit и receipt. Guard/atomic commit остаются обязательными.

Для установки 2.0.30 доступен самостоятельный `scripts/diagnose_enrichment_import.py`:
положить копию скрипта отдельно от программы, открыть PowerShell в папке фактически
используемой программы **Сергея** и запустить её установленным Python:

```powershell
.\.venv\Scripts\python.exe "$env:USERPROFILE\Desktop\diagnose_enrichment_import.py" --app-dir . --xlsx "ПОЛНЫЙ_ПУТЬ\ГСС Биографии.xlsx" --output "$env:USERPROFILE\Desktop\ALE521_diagnostic.json"
```

Имя окружения/папку программы сначала подтвердить по существующему BAT; не
подставлять Owner Windows. Скрипт открывает SQLite mode=ro, использует один read
snapshot и **только читает существующий ключ**. При отсутствии ключа не создаёт
замену. JSON отделяет HMAC valid/invalid/not-tested от текущих карточек и даёт ID,
поля и причины, без ключа, подписей и текстов BIO. Нужны точный фактически загруженный
XLSX и этот JSON; не запрашивать пересылку signing.key, .env или всей REAL базы.
Старые исходники/финал/TEMP не очищать и не заменять до диагностики.

Изолированный lifecycle test подтверждает: restart и update каталога приложения
при том же resolved DB path сохраняют подпись, но очистка TEMP или иной resolved
DB path лишают старый файл проверяемого ключа. Это риск текущего хранения, **не
доказанная причина отказа на чужой машине**. Нельзя переподписывать старый файл или
считать неизменность hidden sheet HMAC PASS. Перенос ключа в постоянное хранилище
не внедрён без подтверждения этого пути отказа в среде Сергея.

`enrichment_recovery.recover` — offline перенос результатов на **новую** подлинную
подписанную выгрузку: обязательный approved research SHA, проверка HMAC свежего
экспорта и соответствия текущим карточкам, уникальных ID, исходных полей, полного
состава наград/номеров и selection. Чистая свежая выгрузка остаётся основой; только
BIO/source/status и разрешённые source assertions переносятся в отдельную копию.
Изменения личности/наград, отсутствующие ID и некорректные данные — отдельный review,
не молчаливое принятие. Исходные ZIP XML hidden/signatures свежего файла сохраняются
побайтно; старые подписи не создаются заново. Существующие BIO в SQLite не изменяются.
До получения свежего экспорта Сергея реальный recovery artifact не заявлять готовым;
TEMP результат не выдавать за пригодный для REAL импорт.

## ALE-524 — компактный результат завершённого импорта

Возврат через top navigation после commit больше не строит workspace: подписанная
производная сводка проверяется по rowid/action атомарного batch receipt в SQLite.
Она создаётся только после commit; ошибка записи сводки не меняет результат
транзакции. При потере сводки/старом импорте она восстанавливается из durable receipt
без classifier/планов/guard всех строк. Исходный preview, signing key, планы,
построчный audit и idempotency ledger не удаляются. Наличие одной сводки без receipt
не означает успех: показывается ошибка с повтором загрузки, resume pointer сохранён.

После подтверждённого success frontend освобождает тяжёлый preview DOM и drafts,
сохраняет token/operation/имя файла и компактный итог. Export/import для новой работы
доступны сразу, общая статистика обновляется отдельно. Полный отчёт и скачивание
построчного аудита доступны по явному действию. Preview/prepare/confirmation,
importing/unknown/failure продолжают прежний resume/reconnect, без повторного POST
на commit. HMAC, BIO/source-FIO/год, stale, concurrent и atomic guards не изменены.

TEMP3489 baseline: server ~2019–2049 мс, 3489 guard, 13965 SQL на возврат.
После исправления первый/повторный возврат новой операции: 29.55/36.69 мс,
reload 45.47 мс; 0 classifier/guard, 6 SQL. На одной TEMP базе из3490 кавалеров
5 HTTP samples: импорт1 строки 28.85–52.24 мс, импорт3489 строк 27.90–30.47 мс,
чистый вход 26.89–31.48 мс. Размер результата ~18 КБ и191 DOM elements, без карточек.
Это измерения isolated Mac runtime, не SLA и не physical Windows profiling.

Пустой быстрый поиск показывает «Ничего не найдено» / «Попробуйте изменить запрос»,
«Найдено: 0» отдельно от общего «Всего». Алфавит скрыт только для пустой выдачи;
found/clear возвращают обычный список. Проверены race старого ответа, HTTP error,
viewport1440/390 и восстановление незавершённого preview/confirmation при3489.
