# Наполнение данных и ручная проверка (ALE-513)

## Контракт после Owner FAIL 25.10.2026

Экран: «Обслуживание данных» → «Наполнение данных»,
`/data-maintenance/enrichment/biographies`. Навигация и соседние экраны сохраняются.

Проверенные дополнения попадают в общий импорт без ручного выбора пустой/найденной
биографии или отдельного принятия года-заглушки. Preview и выбор вариантов не
пишут SQLite: сначала пользователь видит точный набор before→after и источники,
затем отдельно подтверждает запись. Можно импортировать все готовые данные либо
готовую часть одного кавалера. Отложенные через «Пропустить» строки исключаются
из общего импорта до повторного открытия; это состояние браузера, не DB write.

Автоматически допустимы:

- биография ≤2500 Unicode символов только в пустое поле при подтверждённой личности
  и персональной карточке WarHeroes;
- достоверный год той же карточки вместо исходного 1945; исходные ФИО, точная
  награда/степень и номер должны совпадать. Когда номера нет, требуются другие
  независимые подтверждения; одной фамилии/инициалов или заглушки 1945 недостаточно;
- прежний обычный BIO-only импорт «Найдено» остаётся совместимым по своему строгому
  signed identity/source/status контракту и не приобретает скрытых year updates.

Другой исходный год остаётся ручным решением. Его биография может быть импортирована
отдельно, если личность подтверждена. Настоящий 1945 не меняется. Неустановленная
личность/несовпадение награды или номера блокируют перенос: вместо серых
«вариантов» показаны причина, текущие сведения, сведения источника и следующий шаг.
Ермакова (Зайцева) — такой blocker, а не разрешение убрать дополнительную фамилию.
Замена существующей непустой биографии вне scope: текст сохраняется, chooser нет.

После полного сохранения строка имеет disabled «Подтверждено». Частичная —
«Продолжить проверку», только с оставшимися решениями. Статусы считаются по текущей
DB и подтверждённой последовательности собственных операций, не по старому статусу
исследовательского файла. «Строка файла N» и внутренние состояния убраны из UI.
История показывает местные дату/время, actor, поле, источник, прежнее/предлагаемое/
оставленное значение. Pending и пустое→пустое не выдаются за действия.

## Импортная совместимость

Обычная выгрузка не менялась: семь видимых колонок и прежний подписанный hidden
sheet. Оригинальные ID/ФИО/год/награды и HMAC snapshot не редактируются и не
переподписываются. BIO-only XLSX v2.0.29 сам по себе **не содержит** достоверного
отдельного нового года: из биографии его не извлекаем и не выдумываем.

Обновлённая feature-ветка принимает отдельные source assertions:

1. Имеющийся развёрнутый формат с `ФИО в карточке`, `Год в карточке`,
   `Награда в карточке`, `notes`, `Идентификация`, источником и неизменными
   оригинальными snapshot/signature.
2. Копию обычного signed XLSX с дополнительным листом **«Предложения»**:
   `ID кавалера`, `ФИО в источнике`, `Год в источнике`, `Награда в источнике`,
   `Номер в источнике`, `Источник`, `Подтверждённые факты`.
   Необязательная колонка — `Проверка личности`. ID должен присутствовать в
   подписанной книге; дубли, неизвестные ID, формулы, несовместимые источники и
   неправильная структура отклоняются. Эти поля — предложения, не новые оригиналы.

Утверждения источника проверяются против signed identity, диапазонов/лимитов,
точной награды и номера. Пользователь явно подтверждает видимый импорт. Это не
автоматический lookup или независимая загрузка сайта. Legacy 1945 research rule
согласован с импортом; completed worker/artifacts ALE-512 не менялись. Для будущего
производителя нужны эти отдельные поля, а не изменение защищённой исходной колонки.
Production v2.0.29 и прежний physical HEAD 5473ba97 нового auto-year контракта не имеют.

## Безопасность и продолжение

`BEGIN IMMEDIATE` повторно проверяет подпись оригинала, полную identity/награды,
ожидаемые значения всех трёх полей и версию уже сохранённого решения. Обновляются
только `biography`, `birthday`, `fio`; UI этого pass не допускает замену существующей
биографии или неподтверждённое переименование. Нет insert persons/media/migrations.

Audit JSON в существующем `logs(datetime,action,comment)` записывается атомарно с
данными. Bulk receipt и per-person receipts позволяют безопасно повторить тот же
запрос после потери ответа. Ошибка любой строки/audit откатывает всю принятую batch.
После UPDATE проверяется фактический результат. SQLite DATE/NUMERIC может хранить
четырёхзначный год INTEGER: receipt фиксирует реальное значение, без ложного stale.

Собственные изменения подтверждены HMAC receipt с привязкой к hash входного файла,
исходному snapshot и непрерывной последовательности expected before→actual after.
Это рабочее продолжение той же выгрузки, **не** изменение её исходного snapshot.
Посторонняя правка person/award/трёх полей, разрыв/подмена истории, чужой installation
key или неподтверждённый результат блокируют запись. Старые feature receipts можно
проверить по их неизменяемому signed plan; без такого доказательства нужен новый
экспорт. Проверка исходного HMAC всегда предшествует обработке receipts.

Текущий preview хранится в прежней приватной TEMP области 7 дней. Browser session
сохраняет только token/имя файла, фильтр, позицию, активную карточку и pending choices,
не сырой XLSX/биографию. Переход в настоящие «Кавалеры» и назад не требует upload.
«Назад» возвращает в меню, сохраняя работу; «Закрыть файл» требует отдельного
подтверждения и не откатывает сохранённые данные. Финальный checkbox записи после
повторного открытия требует нового явного подтверждения.
