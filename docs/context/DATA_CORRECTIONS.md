# ALE-523 — стандартизация ФИО (на базе ALE-520)

Меню «Обслуживание данных» → «Исправление данных»,
`/data-maintenance/corrections`. «Проверить ФИО» читает все строки person и фактические
поля ФИО (единое fio либо surname/first_name/patronymic и поддержанные эквиваленты по
PRAGMA схемы). Не ограничивается страницей или поиском. Preview — по 50 строк,
показывает было→станет с выделением именно изменяемых символов.

Только таблица Owner: `ABCEHKMOPTXY → АВСЕНКМОРТХУ`, `acekopxy → асекорху`.
Есть кириллический контекст и вся латиница поддержана — запись безопасна. Нет
кириллицы или присутствует неподдерживаемая латиница (включая расширенные Unicode
латинские буквы) — вся запись пропускается. После таблицы исправляется регистр кириллических именных компонентов: первая
буква заглавная, остальные строчные. Пробелы (включая повторные/NBSP), дефисы,
апострофы, точки и скобки сохраняются; ё не заменяется на е. Инициалы И.И. остаются
заглавными; буквы после дефиса/апострофа/открывающей скобки начинают компонент.
Сокращения из нескольких букв перед точкой, пустые/вложенные/несогласованные
скобки, лишние разделители, управляющие символы, нетекстовые поля и другие
алфавиты — отдельные неоднозначные записи, вся запись без изменения. Null/пустые
поля не заполняются. Это не транслитерация и не переименование по источнику.

Один подписанный аудит включает обе причины. safe_records — уникальные записи,
homoglyph_records/case_records — пересекающиеся причины безопасных исправлений;
latin_records считает всю оставшуюся латиницу, включая исключения. Preview по50
показывает старое/новое и причины; перед общим применением — явное подтверждение.
Старые preview с прежней политикой требуют нового аудита, сохранённые receipts
по-прежнему позволяют безопасное восстановление статуса без повторных writes.

«Исправить» вручную применяет только показанный signed audit. Перед записью —
новый SQLite online backup в отдельной `UPDATE_BACKUP_DIR/fio-corrections`, проверка
integrity/schema/counts. Ошибка backup — без записи. Revalidation полного набора
ID/полей ФИО до backup и внутри BEGIN IMMEDIATE после него. Добавление/удаление
строки, изменение имени или состава полей делает preview stale. После UPDATE
проверяется фактическое сохранённое значение. Меняется только фиксированный список
реальных name columns; ID/награды/годы/BIO/media не обновляются. Миграций нет.

Изменения и logs receipt атомарны; журнал содержит before/after/actor/time и числа
записей/символов/путь проверенного backup. Повтор того же operation возвращает
сохранённый результат; pending дубли не создают вторую операцию. Общая OS file lease
вне SQLite/media исключает параллельные импорт и audit/correction. Посторонние
редакторы дополнительно выявляются snapshot revalidation/SQLite transaction.

Оба действия выполняются фоновыми jobs. Прогресс отражает обработанные записи,
страницы backup и реальные фазы; ETA считается по фактической скорости текущей фазы.
Нет искусственных задержек. Пока данных для ETA нет — «Оцениваем время».
100% — только после сохранения preview либо успешного commit. UI остаётся отзывчивым.

Client сохраняет request_id/job_id. Повтор POST после потери ответа использует тот
же ключ. Статус job хранится приватно на диске; после restart незавершённый apply
проверяет атомарный logs receipt: успех только при его наличии. Без доказательства
показывается interrupted и требуется новый аудит; запись вслепую не повторяется.
После успешного исправления повторный аудит показывает 0 безопасных записей,
неоднозначные остатки остаются видны. Старый signed XLSX для изменённых ФИО законно
становится stale: нужен свежий экспорт/исследование, hidden/HMAC не переподписывается.

Проверки только TEMP/Mac и isolated browser. Physical Windows — только разрешённый
launch-only handoff с fresh verified online backup; audit/«Исправить» там нажимает Owner.

## Сводка и вход импорта ALE-523

«Без наград» — число person, для которых нет rewards с тем же person_id,
существующим guide_lev_3.id = rewards.id_name и непустым после bio_blank(name)
наименованием. SQL использует p.id NOT IN (SELECT r.person_id ...), исключая NULL
person_id: множество строится один раз, без зависимого full scan для каждого
кавалера. Номер/дата/instock не участвуют. Дополнительные/пустые/оборванные
технические связи не дублируют людей и не маскируют отсутствие награды. Карточка
самостоятельно пересекается с BIO-подмножествами. Сводка read-only всей БД,
обновляется через существующий /statistics и pageshow, не сбрасывает workspace.

Меню обслуживания: «Наполнение данных», «Исправление данных»,
«Оптимизация изображений», «Импорт новых кавалеров». Последний ведёт на прежний
/persons/import, без изменения создания новых person/rewards и number-only dedup
в точном id_name. Write action доступен лишь в write mode без read_only; readonly
видит название без ссылки, direct GET/POST по-прежнему запрещены сервером.
Back во всех состояниях — /data-maintenance?menu=1, без сброса enrichment resume.
